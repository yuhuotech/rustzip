# 三平台应用内自动更新设计

## 目标与现状

用户在应用内点击“更新”后，看到下载进度；下载完成、校验通过且当前任务结束后，应用退出，由独立更新器安装并重新启动。更新过程中不要求用户打开安装包、手动复制文件或运行安装脚本。需要系统授权时使用系统原生授权提示；用户取消授权时保留旧版本并说明原因。

当前工作区已完成三平台安装交接、独立更新器、签名复验、受限暂存、持久事务、启动回执与失败恢复，并接入 GUI、打包和 CI，正在统一验收。macOS 工作区默认 / 全功能测试、Swift helper 编译和 ZIP / DMG / 回滚 / 中断恢复 / GUI 交接冒烟通过；真实 GPUI 程序创建窗口并完成回执与提交确认的运行测试通过。Linux aarch64 容器普通用户安装、含中文和换行的自定义路径、更新重启、启动失败回滚、中断后启动恢复、卸载及非官方安装拒绝测试通过。Windows 平台封装的交叉 Clippy 检查通过；Windows 原生 CI 和交互授权尚未完成，不能据此宣称已通过全部三平台或正式发布验收。已发布 v0.1.6 的 Windows / Linux 仍走手动流程，macOS 仍以 Launch Services 启动为成功标准；工作区改动不会追溯改变旧客户端。

公共下载先验证签名元数据，对未签名的长度设置 512 MiB 硬上限；GUI 下载到私有目录后分块复验。Windows ZIP 暂存仅接受固定程序、布局和许可证；Linux tar 暂存检查固定资源集合和 ELF 架构，Windows 检查 PE 架构，均拒绝路径逃逸、特殊文件、重复项和超限展开。Linux 版本的可选组件 / 许可证集合变化需要重新运行官方安装器，避免稳定桌面链接出现缺项。

验收脚本：`packaging/windows/test-update.ps1`、`packaging/linux/test-update.sh` 和 `packaging/macos/test-update-helper.sh` 使用隔离目录及专用测试公钥，覆盖更新、启动回执、失败回滚和发布中断后的恢复。`test-fixture` / `updater-test-hooks` feature 及 Swift `RUSTZIP_UPDATER_TESTING` 仅用于 CI，正式打包不启用这些测试入口。交互式 UAC / macOS 管理员 / pkexec 授权接受和取消仍需具有桌面权限的真实环境验收。

## 三平台共用流程

1. 启动时按设置检查 GitHub Release 的 `update.json`；用户点击“更新”后开始下载，并在状态栏显示百分比。稳定版不自动转到预发布版。
2. 后台按清单中的平台和版本下载更新资产，校验大小、SHA-256 和 Ed25519 签名。版本、平台和哈希必须与签名绑定；失败立即停止，旧程序继续运行。
3. 将更新资产、更新任务描述和独立更新器放入当前用户的私有临时目录。更新器再次验证签名与文件内容，并确认目标安装属于 RustZIP 管理的安装；不能仅凭传入的路径覆盖任意文件。
4. 状态栏显示“当前任务完成后更新并重启”。等待排队、运行和暂停的任务及音频播放结束，再正常退出；不强杀进程，也不因更新中断归档写入。
5. 更新器等待原进程结束，暂存新版本，完成版本与完整性检查后发布；保留旧版本直至新版本可启动。失败时恢复旧版本、重新启动并显示可操作的错误提示。异常中断后应能从持久化的更新事务记录恢复。
6. 成功启动后清理临时包、旧暂存和已完成事务；用户设置、密码本、最近文件、任务记录及用户创建的文件不属于更新资产，不得删除。

用户重复点击、多个实例并发更新、磁盘不足、文件占用、断电、授权取消、更新包损坏和启动失败都要有确定结果。每个安装位置的更新需要跨进程互斥；锁或事务记录不能因异常退出而永久阻止后续更新。日志不记录密码、归档内容或完整用户路径。

界面状态沿用现有更新入口：`发现更新 → 下载中（百分比）→ 等待当前任务 → 正在安装并重启`。只在用户点击更新后开始下载；检查更新的开关继续控制后台检查。暂停的任务仍属于未完成任务，用户可以恢复或取消任务后继续更新。

更新任务描述应包含目标版本、平台、资产大小、哈希、签名、下载文件位置、原进程标识及其启动时间、安装位置和事务 ID。更新器从内置公钥独立重新验签；进程启动时间用于区分 PID 被系统复用。清单元数据中的未签名长度不能成为无限制分配依据，下载和解包均需明确的大小、条目数和时间上限。解包必须拒绝绝对路径、`..`、链接逃逸和不受支持的特殊文件。

事务记录只保存恢复所需的受限相对路径、版本和阶段，且必须先校验它属于当前 RustZIP 安装。阶段至少包括“暂存完成”“旧版本已备份或保留”“新版本已发布”“新版本启动已确认”。同一安装位置使用系统级跨进程锁；程序异常退出后，锁自动释放，下一次启动或更新器启动时根据事务记录恢复到一个完整版本。不得信任可被普通用户篡改的事务记录去执行管理员权限文件操作。

重启确认使用一次性随机令牌和私有 IPC：新进程完成基础初始化并创建主窗口后回执事务 ID 和令牌，再接收新的归档任务。更新器检查回执对应预期的新进程和安装路径，收到回执后才清理备份。新进程提前退出时回滚；超时但进程仍存活时先请求其正常退出，若仍不能退出则保留备份并提示恢复，不强杀可能正在处理用户数据的进程。事务记录在每次关键切换前后持久化，恢复过程本身也必须可重复执行。

## 资产与旧版兼容

| 平台 | 手动安装资产 | 新版应用内更新资产 | 兼容旧客户端 |
|---|---|---|---|
| macOS | DMG | 包含已签名 app 的 ZIP | 旧平台键仍指向 DMG；v0.1.5 更新到 v0.1.6 使用 DMG |
| Windows | Inno Setup `.exe` | 包含程序、预览组件和授权文件的 ZIP | 原 `windows-x86_64` 键继续指向 EXE；新增独立签名的 `windows-x86_64-zip` 键 |
| Linux | `.tar.gz` 安装包 | 签名 `.tar.gz`，内含版本化应用目录 | 原 `linux-x86_64` 键和 tar 格式保持可读 |

新客户端按能力优先选择对应更新资产；旧客户端继续选择原平台键，不会下载自己无法安装的 ZIP。每个资产单独签名、单独记录大小和哈希。Release 必须同时校验手动安装包、更新包、平台集合、签名和实际文件，再发布。

已发布的 Windows / Linux 旧客户端没有独立更新器，无法靠服务端清单改变其下载后的行为。因此，首次升级到包含新更新器的版本仍须按旧流程安装一次；以后才可使用本方案。不能通过修改既有 tag、复用已发布版本号或替换已发布资产来掩盖这一过渡。

## Windows

- 保留现有 Inno Setup EXE 作为首次安装、卸载及旧版兼容入口；更新 ZIP 与安装器使用同一构建的 GUI、预览组件、更新器和授权文件。ZIP 中不覆盖既有卸载器及用户数据。
- 更新 ZIP 固定包含 `rustzip.exe`、`rz-updater.exe`、`rz-pdf-renderer.exe`、`rz-video-renderer.exe`、`licenses/` 和版本 / 布局描述文件；不包含 `unins*.exe`、`unins*.dat` 或用户设置。打包与安装器必须从同一批构建输出生成，并由 Release 检查文件集合和架构。
- 更新器在当前应用之外运行，等待旧 GUI 退出。对当前用户安装，将新内容暂存到安装目录同一卷的独立目录，保留原安装中的卸载器及非更新文件；校验后通过可恢复的目录切换发布。安装目录、开始菜单、文件关联与原安装保持一致。
- 对安装在受保护目录的版本，必须走 Windows UAC。提权入口、更新事务和暂存目录应受管理员写入权限保护；提权进程必须重新验签，并核对安装注册信息、实际安装路径和目标文件，不能相信普通用户可修改的任务描述。提权进程不得直接以管理员身份启动 GUI；由原普通用户上下文负责重新启动。
- 普通用户安装由临时目录中的独立更新器处理；更新前先在同卷暂存完整新目录，保留既有安装目录中的卸载器及不属于更新资产的文件。发布时先保留旧目录，再将暂存目录移动到原安装路径；任何失败都按事务记录恢复，不能先删除旧目录。
- 管理员安装的 UAC 引导入口必须来自受保护的已安装程序位置。若更新器自身会被替换，引导进程先把经核验的工作进程和任务复制到仅管理员可写的临时目录，再退出以释放原文件；工作进程重新核对 HKLM 中的 RustZIP 安装记录、路径和更新签名后执行替换。普通用户进程等待工作进程结果，再以原用户身份启动 GUI。临时文件不能成为以管理员权限执行用户可篡改代码的入口。
- 管理员引导进程使用其自身的受保护安装位置和 HKLM 安装记录确定目标；普通用户提供的路径只作交叉核对。受保护工作进程在管理员专用目录中重新读取并验签资产，再构建同卷暂存目录。普通用户进程只接收有限状态和重启通知，不得向已提权进程提供任意命令或可执行路径。
- 替换前注册仅用于未完成事务的登录恢复入口，事务完成后删除。若进程在两次目录改名之间中断，恢复入口可根据注册的安装根和受限事务恢复完整旧目录；系统安装恢复仍请求 UAC。恢复工作进程的文件允许普通用户读取执行，但目录、任务和更新输入不可由普通用户写入。
- 安装包当前没有 Windows Authenticode 签名。Ed25519 更新验签仍是必须的；系统可能显示的 UAC / SmartScreen 提示属于另一层，正式代码签名证书到位后应对安装器及可执行文件签名。
- 更新失败时恢复旧目录和原卸载能力；授权取消、另一个实例仍占用文件、安装目录不是 RustZIP 管理的安装、权限不足等情况必须保留原程序并提示原因。

## Linux

- 官方 tar 安装器将 RustZIP 管理的程序及资源放在当前用户的版本化目录；稳定入口指向当前版本。预览组件、桌面文件、图标、许可证和文件管理器集成都应随同一版本切换，避免只替换主程序后资源不一致。
- 建议目录为 `<PREFIX>/lib/rustzip/releases/<事务标识>/`，由 `<PREFIX>/lib/rustzip/current` 指向当前版本；`<PREFIX>/bin`、桌面入口、图标和文件管理器入口使用指向 `current` 的稳定链接。新版本先在 `releases` 同一文件系统中完整准备并校验，再以原子改名切换 `current`。至少保留上一个有效版本，直到新版本启动确认。
- 安装记录位于 RustZIP 自己的管理目录，记录实际 `PREFIX`、安装时的 `XDG_DATA_HOME` 和布局版本；路径应支持空格、非 ASCII 字符和换行。更新器从真实可执行文件和记录交叉确认安装根目录，不依赖当前会话的 XDG 变量推测旧安装位置。
- 用户级安装的更新器在同一文件系统内解压并校验新版本，通过原子切换稳定入口完成更新；保留上一版本供失败恢复。安装记录保存实际 `PREFIX` 和 XDG 数据位置，不能假设所有用户都使用默认路径。
- 旧版直接安装在 `~/.local/bin` 的用户首次安装新版本时迁移到版本化布局；必须保留设置和已配置的桌面集成。安装记录与目标路径必须校验，不能把任意同名二进制或其他软件目录当成 RustZIP 安装。
- 系统级前缀需要系统授权；授权组件不可用或用户拒绝时应保留旧版本并说明如何继续。由包管理器、Flatpak、Snap、AppImage 或其他外部分发渠道管理的安装，不能绕过其管理器直接覆盖文件；应提供明确提示，并由相应渠道完成更新。只有通过官方安装器创建且路径一致的管理记录，才允许按官方 tar 安装流程自更新。

## 测试与发布验收

- 更新清单：三平台版本与架构选择、旧客户端资产兼容、新客户端优先资产、签名 / 哈希 / 大小篡改、旧版本和预发布规则。
- 更新事务：等待活动任务、正常退出和重启、多个实例竞争、文件占用、授权取消、磁盘不足、部分写入、异常退出、回滚和下一次启动恢复。
- Windows：当前用户及管理员安装、自定义目录、保留卸载器和注册表、UAC 取消、更新前后文件关联、更新失败恢复。必须在真实 Windows runner 验证。
- Linux：默认和自定义 `PREFIX` / `XDG_DATA_HOME`、旧安装迁移、符号链接安全、用户数据不变、安装 / 更新 / 回滚 / 卸载和非 RustZIP 管理安装。必须在 Linux runner 验证。
- macOS：保留既有 ZIP / DMG、Developer ID、版本与 Team 校验、管理员授权及回滚测试。
- 自动化应使用临时用户目录和测试安装，不操作开发者现有安装；覆盖写入失败与进程中断的可控故障。Windows CI 直接验证普通用户路径和受控提权工作进程；真实交互式 UAC 接受 / 取消需在具备桌面的 Windows 会话另行验收。
- 提交前运行格式检查、全工作区 Clippy 和测试；推送发布 tag 后由三平台 CI / Release 构建实际平台包。Windows Authenticode 与 macOS 正式签名、公证状态必须分别报告，不能把本地 ad-hoc 测试当作正式签名验收。
