# RustZIP 测试覆盖率与稳定性提升实施方案

日期：2026-10-24  
状态：**S0 default/all-features 覆盖基线已于 2026-10-25 完成；S1 首批本机可执行变体已实施；S2 已开始并完成 GUI-02/LOC-06 的异步竞态保护与定向回归，其余 S2–S4 仍待实施。结果见 [执行报告](testing-s1-report.md)**  
审查基线：本地 `HEAD=fa98dc4` 加当前工作区全部实现，包括尚未提交的侧栏工具、APK 大小写冲突修正、启动页布局和常用位置重设计。不能仅检出 HEAD 来复现本方案的功能范围。

配套交付：[具体用例清单](testing-stability-cases.md)。本文规定范围、方法、阶段、投入和验收；清单规定输入、故障、预期和落点。

首轮清单包含 **82 个用例族：22 个 P0、60 个 P1**，覆盖文件系统、并发、格式、转换修复、GUI、位置设置、外部服务、发布和性能。它们包括扩展现有测试，不代表要机械新增 82 个测试函数。

## 1. 结论与优先级

当前已经存在较多基础测试，主要问题是**测试集中于常规流程和部分已知缺陷，对文件系统失败、并发竞争、异步交错、真实系统差异和发布产物缺少持续验证**。提高全局行覆盖率本身不足以解决这些问题。

建议分五个阶段实施，先建立可追踪基线，再优先保护用户数据：

1. 建立覆盖率、功能用例和平台矩阵基线，纠正“测试执行过就代表环境已覆盖”的统计方式。
2. 优先验证磁盘失败、路径安全、覆盖保护、同包并发和中断恢复。
3. 覆盖 GUI 异步状态、最近新增功能及真实用户操作序列。
4. 扩展格式交叉验证、属性测试、持续 fuzz、系统原生集成和安装包验收。
5. 用性能、长时间运行和断言质量检查建立发布门槛。

首轮不把新功能开发混入测试提升；测试发现的缺陷用独立小步修复承接，保留复现用例。测试基础设施必须服务于具体风险，避免先做大型通用测试框架。

## 2. 现状盘点及证据边界

### 2.1 数量是静态盘点，不是覆盖率

方案初稿按当时 Rust 源码中的 `#[test]` 和 `#[gpui_kit::test]` 静态计数，共 **278 个测试声明**：

| 范围 | 声明数 | 已覆盖的主要行为 | 主要不足 |
|---|---:|---|---|
| `rz-core` | 6 | 路径基础函数、取消/暂停唤醒 | 未形成完整随机状态序列及跨层状态机验证 |
| `rz-platform` | 4 | 权限、mtime、同文件识别、大小写探针 | 系统目录解析无直接用例；挂载点、重定向、真实卷差异不足 |
| `rz-formats` | 23 | 嗅探、时间、编码、ZIP 并行写入、编解码往返 | 独立生成器交叉验证和各解析器持续 fuzz 不足 |
| `rz-engine` | 70 | 往返、加密、选择性解压、安全、并行、转换/修复 | 文件系统故障注入、发布边界、崩溃/资源上限不足 |
| `rz-app` | 88 | 72 个模块单测、16 个任务队列集成测试 | 同资源并发、故障阶段组合、设置与密码库事务不足 |
| `rz-services` | 7 | HTTP 本地服务、统计字段、系统信息 | 其中真实钥匙串往返默认 ignored；回收站无直接测试 |
| GUI | 64 | 13 个模块单测、51 个无头 GUI 集成测试 | 很多通过直接调用状态方法驱动；原生窗口/输入法、失败后的交互恢复不足 |
| CLI | 14 | 参数、主命令往返、部分错误与覆盖策略 | 退出码、异常输出、信号、中断及 GUI/CLI 合同一致性不足 |
| 发布工具 | 2 | 签名/清单组合、密钥不覆盖 | 实际安装包、启动、升级、卸载与发布门禁不足 |
| **合计** | **278** | 一个测试内部可能循环多个格式 | 数量不能换算成行/分支/场景覆盖率 |

上表是 2026-10-24 的方案制定快照，不是当前测试总数。S0/S1/S2 后的实际执行数以 [执行报告](testing-s1-report.md) 为准：default 为 321 通过 / 3 忽略，`--all-features` 为 327 通过 / 3 忽略。

统计包含 `cfg` 控制和可选 RAR 用例，并不表示每个平台默认运行 278 项。部分测试还在函数体内提前 `return`，例如区分大小写卷上跳过 APK 冲突场景；测试框架仍可能显示成功。后续必须单独报告“适用且执行、适用但未执行、不适用”。

方案初稿制定时**没有运行覆盖率采集、测试、基准、fuzz、安装包或远程 CI**，也没有新装工具。此前本机通过记录可见 [常用位置记录](locations-redesign.md)、[APK 冲突复盘](apk-case-conflict.md)、[侧栏实现记录](sidebar-implementation.md)，不能当作本次重新验证结果。后续 S0 覆盖率采集和 S1/S2 测试结果见 [执行报告](testing-s1-report.md)；分支覆盖率及平台、fuzz、安装产物证据仍为**未知/未覆盖**。

### 2.2 当前基础设施

| 项目 | 当前可见状态 | 影响 |
|---|---|---|
| 常规 CI | `.github/workflows/ci.yml`：核心三平台，GUI macOS/Windows；默认和全 feature 核心检查 | 配置存在不等于当前工作树已在三平台通过；Linux GUI 未进入矩阵 |
| 覆盖率 | 未见采集、分模块报告或增量门槛 | 无法追踪新增实现的未执行区域 |
| Fuzz | 只有 `fuzz/fuzz_targets/zip_recovery.rs`；CI 未调度，语料目录被忽略 | 不能代表 ZIP 正常读取、7z、tar、单文件流和路径处理均受持续保护 |
| 性能 | `throughput` 基准和 32 MiB CI 冒烟 | 部分失败只打印/忽略返回值，没有可靠的正确性失败门槛和历史回归比较 |
| 格式样本 | 多为自身生成；仓库记录的 RAR 外部样本只有一个 87 字节 RAR4 | 自己写、自己读可能共同漏检同一错误；RAR5/固实/密码等代表性不足 |
| 发布流水线 | `.github/workflows/release.yml` 打包、签名、发布；Linux experimental | 未见发布前强制调用完整测试及安装产物验收；失败/缺平台的发布条件需要验证 |
| 系统集成 | 钥匙串测试默认 ignored；回收站依赖真实系统；GPUI 平台验证仍有未完成项 | 无头测试不能替代实际登录会话、系统授权、原生渲染和输入法 |
| 测试稳定性 | 有真实 sleep、并发任务及环境条件分支 | 可能出现偶发失败，不能靠无限重跑维持绿色 |

### 2.3 优先审查的风险落点

下表是**基于源码的风险假设**，不是本轮已复现的漏洞结论；实施时先写失败用例再判断。

| 落点 | 需要优先证明的性质 | 为什么常规往返不能证明 |
|---|---|---|
| `rz-engine/src/safe_path.rs`、`extract.rs` | 已存在的目标父目录链接、目标文件链接和 Windows junction 不得导致越界写入；预检后发生替换仍安全 | 现有“跳过包内 symlink”不等于防住目标目录中的链接 |
| `rz-engine/src/compress.rs` | 固定 `.rz-part` 临时名在同目标并发下不互相污染；finish/rename 失败不损坏已有结果 | 正常完成和单次主动取消没有覆盖这些发布时机 |
| `rz-app/src/modify.rs` | 同进程同包操作不互删含 PID 的暂存目录；两个编辑不发生静默丢失更新 | 当前测试主要顺序调用；先解包再替换扩大了竞争窗口 |
| `rz-app/src/settings.rs`、GUI 保存调度 | `.tmp`、rename、同步失败、多个保存者和进程退出不破坏最后有效设置 | 原子保存正常路径不代表失败、跨进程竞争也正确 |
| `rz-app/src/preview.rs`、7z/tar `open`、GUI 图片解码 | 解码/后端内部缓冲受预算与取消约束，体积很小但像素巨大的图片也安全 | 外层 `take(limit)` 不必然限制格式后端在返回 Read 前的工作 |
| `rz-services/src/keychain.rs`、GUI 密码任务 | 密码写入成功但索引失败、删除成功但索引失败、锁定和并发不会虚报成功或丢失其他密码 | 内存库成功流程和“全程失败”假实现未覆盖半成功事务 |
| GUI 打开、目录重载、预览、任务结果 | 后发请求先完成、关闭标签/窗口后回调、快速切页不会覆盖新状态 | 一次操作再等待完成的用例没有制造乱序 |

## 3. 覆盖率与稳定性如何量化

### 3.1 分开报告四类指标

1. **代码覆盖**：生产 Rust 代码的行/区域/函数覆盖，按 crate 和关键文件报告；默认和 `rar` 分别采集。第三方源码、测试夹具、图标生成器不混入分母。
2. **异常场景覆盖**：配套清单中每个用例族的适用变体是否执行，并满足所有断言。不能用总测试数代替。
3. **平台覆盖**：OS × 文件系统大小写 × feature × 原生/无头环境，逐格展示证据；macOS/Linux 的条件代码不能合并成“所有平台都已测”。
4. **测试有效性与稳定性**：核心保护条件被变异后测试能否发现；重复运行有无不稳定失败；失败能否凭种子和故障点复现。

Rust 分支覆盖另设实验报告：首期使用固定 stable 工具链采集行/区域覆盖；只有验证 nightly 和工具兼容性之后，才加入分支覆盖门槛。不能把行覆盖率称作分支覆盖率，也不能将不同平台/条件报告简单求平均或相加。

### 3.2 拟定门槛，建立基线后校准

这些是**未来实施目标**，不是现状数值，也不直接修改当前规范。

| 阶段 | 代码覆盖目标 | 质量硬条件 |
|---|---|---|
| S0 基线 | 完整产出首份报告；暂不因旧代码低于任意比例阻塞整个项目 | 未覆盖文件、忽略项、条件跳过和平台空白必须可见 |
| S1 数据安全 | 新增/修改的核心逻辑行覆盖建议 ≥85%；关键安全/发布保护文件 ≥90% | S1 交付范围的 P0 适用变体 100% 执行并通过，无已知数据损坏/越界/死锁；S3 中的格式/系统 P0 仍列待验证，不能提前发布豁免 |
| S2 用户流程 | GUI 状态与应用逻辑的本次增量覆盖建议 ≥85%；核心总体分阶段达到 ≥85% | 已支持平台的关键流程矩阵全通过；切页/取消/错误后可以继续操作 |
| S3–S4 巩固 | 核心生产代码行覆盖目标 ≥90%；成熟后关键分支覆盖建议 ≥80% | 不以覆盖率豁免 P0；候选版本完成产物、长跑、格式交叉验收 |

若基线已高于目标，不得倒退。若某模块因外部后端、平台不可用而不能达到目标，应列出具体文件、未执行原因和补测任务，不把整个模块从报告中删除。GUI 渲染样式覆盖率只作诊断，不追求用重复截图将百分比刷高。

建议优先在路径安全、发布保护、覆盖决策、更新验签和状态迁移函数上做变异测试。初期逐个审查 surviving mutant；成熟后有效变异杀死率目标 ≥80%。等价变异、无法编译和超时单列，不将超时一概视为测试成功发现错误。

## 4. 先定义测试必须保护的结果

以下是拟采用的验收契约。若与已确定产品决策冲突，应单独提出决策变更；不能为了让测试变绿而放宽数据安全预期。

| 操作 | 成功必须证明 | 失败/取消/崩溃必须证明 |
|---|---|---|
| 新建压缩 | 路径集合、内容哈希、目录/空文件、可保留元数据正确；报告与实际一致 | 源文件不变；默认不覆盖既有目标；失败结果不冒充成功；临时文件可识别且不会误删他人文件 |
| 解压 | 输出实际内容一致；选择性解压不混入未选项 | 不越界；默认模式保全既有文件；不得留下被当作成功的截断文件。已完成条目允许保留，但任务须明确为部分完成/失败，**不承诺全目录事务回滚** |
| 显式覆盖解压 | 明确覆盖策略后替换正确文件 | 期望单文件替换失败保全旧文件；若现实现做不到，作为缺陷修复，不用“用户点过覆盖”豁免截断风险 |
| 包内编辑 | 校验后的完整新包成为唯一有效结果；未修改条目一致 | 发布前原包字节哈希不变；发布后只能是完整新版本；同包竞争串行、拒绝或检测版本冲突，不能静默丢更新 |
| 转换/修复 | 独立校验目标；修复恢复/跳过数量与内容吻合 | 不覆盖源/已有输出；坏条目不伪装恢复；取消后无成功产物；报告不隐藏丢失 |
| 任务队列 | 生命周期合法、并发上限有效、每个任务恰有一个终态 | 无永远等待、重复终态和暂停后退出挂死；发布前取消不能发布，发布后到达的取消不能伪称已经回滚 |
| 设置/密码 | 重启读到预期数据，操作结果与持久化结果一致 | 老的有效数据保持可用或有明确可恢复状态；失败不报“已保存”；不泄露密码 |
| GUI | 每个操作有清楚反馈，焦点和目标对象正确 | 错误结束后仍能打开/重试/切页；过期回调不污染新页，不执行已经关闭对象的后续动作 |

每个数据安全用例至少断言：返回值/错误码、源文件哈希、旧目标哈希、实际输出路径集合、目标外哨兵、临时文件集合、任务终态和超时上界；GUI 用例再断言可见提示与下一步可操作。不是所有测试都需要八项，但必须写明哪些不适用。

## 5. 测试基础设施的最小建设

### 5.1 用例驱动的故障注入

- 在自有读写、finish、sync、rename/persist、设置保存和密码库边界引入小范围可替换接口；优先沿用 `Read/Write`、`ArchiveReader/Writer`、`SecretStore`、`Fetcher` 和 `Sender`。
- 对“第 N 次写入失败”“返回短写”“读取 N 字节后 EOF”“finish/rename 失败”提供可指定命中次数的实现；测试须验证故障点真的命中，防止测到错误的早退分支。
- 不全局替换文件系统，不在生产热路径引入大锁或测试运行时；需要真实 OS 错误的少量用例在临时受限卷/隔离用户运行。
- 仅 `chmod` 不足以模拟所有权限失败，管理员/root 环境可能绕过；确定性注入和真实卷验证分别记录。
- 进程强杀以独立测试子进程在命名检查点暂停，父进程确认检查点后终止；不能靠随机 sleep 猜它是否正在 rename，更不能给开发者正在使用的 RustZIP 发信号。

拟新增位置：`crates/rz-engine/tests/support/fault_io.rs`、`crates/rz-app/tests/support/fault_store.rs`、`tests/support/manifest.rs`。名称仅为计划，不要求先创建大公共 crate。跨层共用代码达到实际复用规模后再抽出，依赖方向不变。

### 5.2 可独立判断对错的内容清单

生成源树清单：相对路径、类型、字节数、SHA-256、权限/mtime（按平台能力比较）；解压或转换后与清单对照。CRC 通过不能替代路径集合和原始内容比对。不要只用 RustZIP 自己再次打开输出作为唯一真值。

时间戳按格式精度比较，例如 ZIP DOS 时间两秒粒度；不跨平台机械断言 inode 或 Unix mode 一致。符号链接的当前能力是压缩/解压跳过、转换拒绝、修复报告跳过，并保留目录丢失时属性不可辨认的明确警告，不能把暂未支持的链接保真功能当作已承诺能力。

### 5.3 让并发和 GUI 回调可控

- 用 barrier/channel/checkpoint 控制“枚举完成、开始写入、校验完成、发布前、发布后”的时序。
- GUI 为打开、目录扫描、图片预览、密码库与保存任务提供可延迟完成的服务替身；主动制造 A→B 请求但 B→A 返回。
- 验证真实事件序列及终态唯一性；虚拟时钟用于提示消失、保存稳定窗口和轮询，减少真实 sleep。
- 并发用例采用固定种子随机操作序列，并保存种子、平台、feature 和输入摘要；关键序列每夜重复 100 次，发布前 1,000 次。外部进程监督每次运行，超时保存状态后终止，不能挂住整个 CI。
- `loom` 只作为后续可行性实验，先验证能否隔离小型同步状态机；不要求把 GPUI 或全部格式库迁移到另一套同步原语。

### 5.4 夹具与语料

将稳定的最小夹具、生成器、来源和许可证说明提交到仓库；动态 fuzz corpus 由 CI 缓存/产物保留。固定 seed 夹具不能仅存在开发机 `/tmp`。

- 每份夹具记录生成工具及版本、格式/算法/密码配置、预期文件清单、哈希、来源许可、损坏方式。
- APK 大小写冲突使用自制微型 ZIP/APK 复现，不依赖开发者 Downloads 或未经许可分发真实 APK。
- RAR 使用合法获取且可再分发的外部样本，补 RAR5、固实、密码及损坏变体；RustZIP 不实现或链接 RAR 压缩器。
- 大文件、ZIP64 和大量条目按需生成；磁盘预算和超时明确。稀疏文件不能替代所有“真实读取大量数据”的压力验证。
- 错误路径/本机测试目录允许存在于私有测试产物，公开失败报告做脱敏；密码、用户源文件和真实钥匙串记录不进入夹具。

### 5.5 属性测试先覆盖这些不变量

| 纯逻辑范围 | 随机输入 | 不变量 |
|---|---|---|
| 路径预检 | 分隔符、盘符、Unicode、深度、保留名、重复路径组合 | 不安全路径不能进入写入计划；允许的相对路径不逃离逻辑根；真实链接逃逸另用 FS-04/05 验证 |
| 浏览模型 | 随机目录树、排序、过滤和选择序列 | 排序不改变条目身份和总量；子目录查找/面包屑一致；返回上级不变成可删除条目 |
| 常用位置 | 随机成功/失败打开、移除、重开、序列化重启 | MRU 有界、同目录去重、隐藏不被旧记录回填复活；成功重新使用才恢复 |
| 数据预算/进度 | 声明值边界、短读、超长读、取消/暂停序列 | 不超过授权输出预算；已知总量时进度不越界；未知总量不假造百分比；终态后不继续写入 |

每类先运行固定种子的少量输入，保留失败最小样本，再扩大每夜预算；不对磁盘字节、墙钟时间和复杂多线程直接做无约束随机生成。

## 6. 格式、环境与交叉验证矩阵

### 6.1 按真实能力建立分母

| 当前格式族 | 每 PR 必测 | 每夜/发布前补充 | 不适用项 |
|---|---|---|---|
| ZIP / ZIP 容器 APK、JAR、DOCX | 普通/空/边界往返、损坏、选择性、安全、AES、错误密码、路径与内容清单 | ZIP64、descriptor、多算法、注释/extra、旧编码、外部工具产生的样本 | APK 应用安装正确性不属于压缩软件承诺；改包会破坏应用签名，不声称可重新安装 |
| 7z | 普通/固实、空条目、密码与加密头、损坏、取消、转换/恢复 | 多块、块中损坏、不同工具版本、声明巨大字典/内存预算 | 头部严重损坏不保证恢复全部内容 |
| tar / tar.gz / tar.xz / tar.zst / tar.bz2 | 七种归档目标中的 tar 系列逐格式成功/失败及选择性 | PAX/GNU 长名、链接/特殊节点、截断、复合流、元数据 | 不做这些格式的密码加密；应明确拒绝 |
| gz / xz / zst / bz2 单文件流 | 单文件往返、非单文件输入拒绝、测量大小限制、取消 | 多成员/串联流、截断/尾随数据及超限前置解码 | 无多条目浏览、无加密、不能作为多文件归档目标 |
| RAR（feature 开/关） | 开启时读取最小样本，关闭时明确识别并拒绝；禁止写 RAR | RAR4/5、密码/固实/损坏、转换源 | 无 RAR 压缩；关闭 feature 不计作“已测试 RAR 解压” |

`product.md` 仍列出 lz4、ISO、CAB、WIM 等路线图需求，当前后端没有这些完整能力。首轮对其做“明确不支持/不崩溃”验证，不把未来功能纳入已实现格式的往返覆盖率分母。

使用外部 7-Zip、系统/bsdtar/libarchive CLI 做独立 oracle：外部生成→RustZIP 读取，以及 RustZIP 生成→外部读取→内容清单。只调用独立进程，不复制或静态链接 7-Zip 源码，不将外部工具捆入产品。每种工具仅参与它实际支持的单元格，缺工具不是 PASS。

### 6.2 环境矩阵

| 平台 | 必选环境 | 专项 |
|---|---|---|
| macOS | Apple Silicon 本机 + 固定 runner；默认 APFS 与临时区分大小写 APFS | 原生红黄绿按钮、最小窗口/全屏、Retina、输入法、Keychain 锁定/授权、Finder 打开方式 |
| Windows | NTFS、普通用户；Windows 10/11 按最终声明的最低支持线验收 | Known Folder 重定向、长路径/保留名、文件占用/共享模式、junction、Credential Manager、DPI、Recycle Bin、安装/升级 |
| Linux | 固定发行版及 ext4；XDG 配置和 Secret Service 有/无两种会话 | X11/Wayland、缺 GPU/软件驱动探测、缺字体、外置/只读挂载、垃圾箱服务缺失、发行包依赖 |

核心三平台矩阵保留；Linux GUI 先建立依赖与软件渲染可行性任务，失败明确保留为缺口，不能跳过后仍声称三平台桌面稳定。GUI 框架最终选型依然遵守 D3 和 [GPUI 验证清单](gpui-probe.md)，本方案不替它定案。

## 7. CI 分层与失败证据

| 触发 | 执行内容 | 初始预算（不含首次依赖编译，S0 实测校准） | 失败处理 |
|---|---|---|---|
| 每 PR | fmt/Clippy；三平台核心 default+RAR；macOS/Windows GUI；P0 故障用例；固定 corpus 回放；增量覆盖 | 快速检查目标 ≤15 分钟；重型检查独立 job | 必须通过；首次失败保留，不以自动重跑覆盖原失败 |
| 每夜 | 格式交叉、故障点扩展、随机并发、fuzz、真实卷、Linux GUI 探测 | 核心扩展目标 ≤45 分钟；fuzz 每目标 10–20 分钟，各 job 有总超时 | 自动产出最小复现；安全/数据损坏缺陷标记阻止发布 |
| 每周/候选版 | 4 小时混合任务长跑、句柄/内存、原生会话、变异测试、安装包 smoke | 资源受限测试机，独立于 PR runner | 查明增长/崩溃/泄漏；不能通过重启掩盖累积问题 |
| 发布前 | 相同候选提交和构建配置的全部必选任务、真实包安装/启动/打开/解压/退出；签名清单核对 | 各必选产物均有验收报告 | 尚缺的平台、产物、测试或关键超时不得发布成正式支持版本 |

后续拟新增 `.github/workflows/coverage.yml`、`nightly-stability.yml`、`artifact-smoke.yml`，或按实际维护成本合并。先修现有 benchmark 的“错误仅打印”问题，确保正确性失败退出非零，再讨论速度波动阈值。受负载影响的绝对性能测试不应混入随机共享 runner 的普通单元测试硬门槛。

覆盖率先存本地/CI artifact 的 HTML、LCOV/JSON 和分模块摘要；不默认上传外部覆盖率 SaaS。工具版本和 Rust 工具链固定，不在每次 job 安装无限制 latest。默认/RAR及 OS 报告各自保留，确需合并时验证工具支持、源码版本和统计口径一致。

每次失败产出：用例 ID、源码提交与工作区标识、OS/架构/文件系统特性、feature、生成种子、故障命中点、预期/实际、目录清单及哈希差异、任务事件、超时栈/子进程退出码、GUI 截图。标准 artifact 建议保存 14 天，候选版报告保存到版本归档；超过预算的巨型文件只保留生成器、种子和摘要。

## 8. 分阶段任务、投入与退出标准

投入估计基于一名熟悉 Rust/GPUI 的工程师，设备和 CI 权限可用；单位为有效工程人日，不是承诺日历工期。Windows/Linux 环境准备及发现的重大架构问题另计。每阶段交付可单独审查，先完成 S0–S2 再扩大投入。

| 阶段 | 预计投入 | 具体产出 | 退出标准 |
|---|---:|---|---|
| S0 基线与合同 | 1–2 人日 | 固定工作树基线；测试索引；覆盖率工具 PoC；skip/NA 清单；夹具清单模板；风险契约审查 | 一条可复现命令产出分模块报告；不虚报覆盖比例或平台通过 |
| S1 数据安全与资源竞争 | 4–6 人日 | FS/TASK/配置事务的首批 P0 变体；命名检查点与最小 I/O 注入；原包/旧目标哨兵；关键失败修复；发布路径数据保护 | S1 范围 P0 适用变体通过；同目标/同包并发无丢数据；磁盘失败/强杀无坏包替换好包 |
| S2 GUI 可恢复性与新增功能 | 3–4 人日 | GUI/LOC/PREVIEW 矩阵；可控回调/虚拟时间；真实点击序列、布局断言、英文/中文错误和重启检查 | 关键页面无陈旧回调、错误后仍可操作；已知历史回归稳定通过；低频延迟不使 UI 阻塞 |
| S3 格式与系统验收 | 4–6 人日 | FMT/TRANS/SVC/REL 扩展；外部样本和 oracle；多解析器 fuzz；系统集成与安装包 job | 已实现格式的适用矩阵执行；fuzz 可复现并持续运行；必选产物和系统集成证据齐全 |
| S4 长跑、性能与断言质量 | 2–3 人日 | 性能正确性门禁、同机重复采样、资源长跑、关键函数变异；覆盖率阶段目标 | 无 P0/P1 未关闭；核心覆盖目标与候选版质量门禁达成；剩余限制明确 |
| **合计** | **14–21 人日** | 第一轮完整稳定性工程 | 实际新增测试量由变体展开和基线缺口决定，不以“凑够 N 个测试”验收 |

建议 S1 首批按 `FS-01、FS-03、FS-04、FS-05、FS-06、FS-07、FS-10、TASK-03、TASK-04、TASK-06` 实施；这些直接保护磁盘数据、路径边界和并发终态。S2 优先 `GUI-01、GUI-02、GUI-04、GUI-05、GUI-07、LOC-06`。先扩已有用例的关键断言，已有充分覆盖的变体只登记证据，不重复造同义测试。

阶段开始时将每行用例拆成“夹具/注入点→测试→必要修复→平台验证→证据”任务。角色分配为：核心实现负责 FS/TASK/FMT/TRANS；GUI 实现负责 GUI/LOC；平台与发布维护负责真实系统 SVC/REL；同一人可兼任，但 P0 的安全契约与失败证据需要独立复核。每阶段报告应列出完成 ID、失败 ID、未覆盖平台、覆盖率变化、耗时和下阶段阻塞项。

## 9. 验收和发布规则

- P0：越界写入、已有数据丢失/损坏、未校验包替换原包、密码泄露、死锁/不可退出等，**零容忍发布**。
- P1：主操作失败、错误后不可恢复、对象/路径操作错误、已支持平台不能启动、关键 UI 被遮挡等，候选版必须关闭。
- P2：次要布局、文案或性能优化等，可明确记录剩余影响和补测范围；涉及真实数据损坏时不能降为 P2。
- 任何“改进异常测试时发现的实现缺陷”都需要测试先失败、局部修复后通过，再跑相关矩阵及规范检查。不能只在报告中标为预期失败后长期豁免。
- 不能把受条件限制的用例静默 return 当作已验证。能力不支持是 NA；能力承诺存在但环境缺失是未覆盖，二者不能混写。
- 实际安装包、真实系统集成、GUI 输入法/渲染和无头测试分开签出结论。无头 100% 通过不能代替真实桌面可用性。
- 稳定性表述应是“哪些平台、格式、故障场景已验证及限制”，不使用“绝对无 bug”“达到某覆盖率即可保证稳定”等结论。

## 10. 后续实施入口与工具依据

本方案最初只定义计划。后续实施已经开始；当前 S0/S1 结果、测试命令与覆盖率数据以 [S1 执行报告](testing-s1-report.md) 为准。本节保留可复现入口和后续阶段任务。

### S0 的具体操作顺序

1. 固定包含当前未提交实现的可复现源码快照，记录工具链/依赖锁/feature；不得直接丢弃工作区改动来制造基线。
2. 导出实际编译配置的测试列表，分别核对 default、RAR 和三个 OS 的条件用例；与本文静态计数对齐，识别 ignored 和函数体提前退出。
3. 已验证 `cargo-llvm-cov 0.9.1` 能采集 default 与 all-features 的 workspace 无头测试，包括 GUI；本机 JSON 与分 crate 结果见执行报告。分支计数当前不可用。
4. default 与 all-features workspace 测试已运行；跨进程编辑、同目标竞态和设置保存等重点并发变体已执行。关键回调测试 20 次重复、更多随机压力仍待 S2/S4。
5. 将清单每个用例族标注已有充分证据/需要扩展/未实施，拆出 S1 的第一批 P0，确定实际 CI 预算和覆盖率基线。

基础回归命令如下；当前覆盖工具版本和本轮覆盖率命令已记录在 [S1 执行报告](testing-s1-report.md)。

```sh
cargo fmt --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --exclude rustzip-gui --exclude gpui-probe
cargo test --workspace --exclude rustzip-gui --exclude gpui-probe --all-features
cargo test -p rustzip-gui
RZ_BENCH_MB=32 cargo bench -p rz-engine --bench throughput
```

本轮确认可直接用 `cargo llvm-cov --workspace --exclude gpui-probe` 及 `--all-features` 变体采集包含 GUI 的本机报告。矩阵 CI 仍须按平台分别采集；不在缺少图形栈的 Linux runner 直接声称 GUI 命令可运行。

候选工具只用于开发/测试，不自动加入产品依赖；采用前按项目许可证规则审查并记录版本。已有 GPUI 无头测试和 Rust 测试框架继续复用，`proptest` 用于纯逻辑性质，`cargo-fuzz` 用于不可信解析，`cargo-mutants` 用于检查断言是否有效；不同时引入多套功能重复的测试运行器。
